# 3D 미니룸 MVP 개발 프로세스

Sep 30, 2026 · @현철

## 전체 흐름

다음 할 일은 ERD나 API 명세가 아니라 1주짜리 기술 검증이다. 가장 불확실한 것(3D 성능, 에셋 제작, 로그인)이 되는지 먼저 확인하고, 그다음에 설계를 확정한다. 1인 개발 기준으로 MVP 출시까지 약 9\~10주를 잡았다.

기술 검증에서 기준을 못 넘으면 설계로 가기 전에 PRD 범위를 줄이고 다시 검증한다. 지인 테스트에서 D7 리텐션 25%를 넘어야 베타 기능으로 간다.

## 1단계. 기술 검증 (1주)

ERD나 API 명세보다 먼저 "이게 정말 되나?"를 확인한다. 설계 문서는 나중에 고칠 수 있지만, 3D 방이 PC에서 버벅이면 서비스 자체가 성립하지 않는다.

| 검증할 것 | 만들 것 | 완료 기준 |
| --- | --- | --- |
| 에셋 파이프라인 | Blender + Claude로 가구 3종(침대, 컴퓨터 책상, 화분)을 만들어 glb로 내보내고 gltf-transform으로 압축 | 가구 1개 100KB 이하, 팔레트 텍스처 1장 공유, 1개 제작에 2시간 이하, 3종을 나란히 놓았을 때 같은 스타일로 보임 |
| 3D 방 렌더링 | Three.js로 8×8칸 방, 고정 쿼터뷰 카메라, 바닥과 벽지 교체 | 내장 그래픽 노트북에서 30fps 이상 |
| 가구 배치 | 그리드 스냅 드래그, 90도 회전, 칸 단위 겹침 판정 | 가구 30개(3종 복제)를 깔아도 드로우콜 100회 이하 |
| 저장과 복원 | 배치를 "기준 칸 + 회전" JSON으로 만들어 새로고침 후 그대로 복원 (브라우저 저장소로 충분) | JSON 1개 10KB 이하, 3×2 가구를 회전해도 복원 위치가 같음 |
| 로그인 | Spring Boot + Google OAuth2 로그인 한 번 성공 | 로그인 후 내 이메일이 화면에 표시 |

에셋 제작 시간이 중요한 이유는 17종을 저녁마다 나눠 만들 수 있는지가 일정의 가장 큰 변수이기 때문이다. 1개에 2시간을 넘기면 가구 수를 줄이거나 무료 에셋을 섞는 쪽으로 PRD를 고친다.

프론트엔드는 이 단계에서 Three.js를 직접 쓸지, React Three Fiber(+ drei)를 쓸지 정한다. React로 가구 목록 패널과 방명록 UI를 함께 만들 것이므로 R3F가 상태 연동과 드래그 구현에 유리하다. 검증 코드를 R3F로 짜 보고 불편하면 바꾼다.

이 단계의 코드는 버려도 된다. 목적은 코드가 아니라 "된다, 안 된다"라는 답이다. 기준을 못 넘는 항목이 있으면 설계로 가기 전에 PRD 범위부터 줄인다.

## 2단계. 설계 (1주)

설계는 화면 흐름, API 명세, ERD 순서로 한다. 화면이 어떤 데이터를 보여줄지 정해야 API가 나오고, API가 주고받는 데이터가 정해져야 테이블이 나온다.

**화면 흐름**: MVP 화면은 6개다. 종이에 그리거나 Figma로 간단히 그려도 충분하다.

1. 방 보기: 친구 방 3D 화면, 투데이/토탈, 방명록 패널, "내 방 만들기" 버튼
2. 로그인: Google 로그인 버튼 하나. 로그인 전에 보던 방 주소와 쓰던 방명록을 브라우저에 저장해 두고, 로그인이 끝나면 그 방으로 돌아와 복원한다
3. 첫 가입: 닉네임 입력, 만 14세 이상 확인, 약관과 개인정보처리방침 동의
4. 꾸미기 모드: 내 방 + 가구 목록 패널, 바닥과 벽지 선택, 저장 버튼
5. 공유: 내 방 링크 복사
6. 모바일 안내: "PC에서 열기"와 내 PC로 링크 보내기

**API 명세 초안**: Spring Boot에 springdoc-openapi를 붙이면 코드에서 Swagger 문서가 자동으로 만들어진다. 명세는 아래 표로 시작해서, 구현하면서 Swagger로 옮긴다.

| 메서드 | 경로 | 로그인 | 설명 |
| --- | --- | --- | --- |
| GET | `/oauth2/authorization/google` | 아니요 | Google 로그인 시작 (Spring Security 제공). 첫 로그인 때 내 방 자동 생성. 성공하면 프론트엔드의 `/auth/callback`으로 리디렉션 |
| GET | `/api/me` | 예 | 내 정보, 닉네임 설정 여부, 내 방 slug, 새 방명록 개수 |
| PATCH | `/api/me` | 예 | 닉네임 설정 (2\~12자, 중복 허용), 14세 이상 확인, 약관 동의 기록 |
| DELETE | `/api/me` | 예 | 탈퇴. 계정, 방, 내가 쓴 방명록 삭제 |
| GET | `/api/rooms/{slug}` | 아니요 | 방 주인 닉네임, 바닥, 벽지, 가구 배치 JSON, 투데이/토탈 |
| PUT | `/api/rooms/me/layout` | 예 | 내 방 바닥, 벽지, 가구 배치 저장. 가구 30개 초과, 겹침, 방 밖 좌표는 거절 |
| POST | `/api/rooms/{slug}/visits` | 아니요 | 방문 기록. 같은 방문자는 하루(KST) 1회만 투데이 증가, 방 주인 본인은 제외 |
| GET | `/api/rooms/{slug}/guestbook?page=0` | 아니요 | 방명록 목록, 최신순 20개씩 |
| POST | `/api/rooms/{slug}/guestbook` | 예 | 방명록 작성 (500자 이하, 1인당 1분에 3개까지) |
| DELETE | `/api/guestbook/{entryId}` | 예 | 방명록 삭제, 방 주인 또는 글쓴이만 가능 |
| POST | `/api/events` | 아니요 | 지표용 이벤트 기록 (공유 링크 유입, 모바일 안내 진입 등) |
| GET | `/s/{slug}` | 아니요 | 공유 링크. OG 태그(제목 "○○님의 미니룸", 공통 이미지)를 담은 HTML을 내려주고 프론트엔드 방 주소로 이동시킨다. 모바일이면 안내 페이지로 보냄 |

공유 링크를 백엔드 경로(`/s/{slug}`)로 두는 이유는 카카오톡 같은 메신저가 링크 미리보기를 만들 때 JavaScript를 실행하지 않기 때문이다. 정적 호스팅에 올린 SPA로는 방마다 다른 OG 태그를 줄 수 없다. 이 경로를 거치면서 `share_open` 이벤트도 함께 기록한다.

방 주소에 순번 ID 대신 랜덤 slug(예: 8자리 영숫자)를 쓰면 주소를 하나씩 바꿔 가며 남의 방을 훑어볼 수 없다. 베타의 비공개 방 설정도 이 전제 위에서 쉬워진다.

가구 목록(17종의 ID, 이름, 크기, glb 경로)은 DB에 넣지 않고 프론트엔드의 JSON 파일로 관리한다. 백엔드의 배치 검증에도 크기 정보가 필요하므로 같은 JSON을 백엔드 리소스로 복사해 쓴다. 가구가 늘어나는 베타에서 DB로 옮긴다.

## ERD 초안

MVP 테이블은 5개다. 가구 배치를 테이블로 쪼개지 않고 rooms의 JSON 칼럼 하나에 통째로 저장하는 것이 구현량을 가장 크게 줄이는 결정이다.

&#91;embedded content: ERD 초안 · MVP 테이블 4개\]

위 다이어그램에 아래 변경을 반영한다.

| 테이블 | 추가, 변경 | 이유 |
| --- | --- | --- |
| users | `nickname`, `age_confirmed_at`, `terms_agreed_at` 추가 | 실명 노출 방지, 14세 확인과 약관 동의 기록 |
| rooms | `slug` (unique) 추가. 외부 노출은 id 대신 slug만 | 방 주소를 추측할 수 없게 함 |
| room_daily_visits | `(room_id, visit_date, visitor_key)` unique 제약 | 하루 1회 카운트를 DB에서 보장 |
| events (신규) | `id, user_id(nullable), visitor_key, type, room_id(nullable), ref, device, created_at` | 초대 전환율, D7 리텐션, 기기별 집계 |

새 방명록 개수는 `guestbook_checked_at` 이후에 쓴 글을 세면 나오고, `guestbook_checked_at`은 주인이 자기 방의 방명록 패널을 열 때 갱신한다. 투데이는 오늘 날짜의 `room_daily_visits` 행 수, 토탈은 그 방의 전체 행 수다. 비로그인 방문자는 쿠키에 담은 임의 ID를 `visitor_key`로 쓰고, 로그인하면 그 `visitor_key`를 `users`에 저장해 가입 전 방문 기록과 연결한다.

`visit_date`와 모든 날짜 집계는 한국 시간 기준이다. 시각은 `timestamptz`로 저장하고, 방문 날짜는 앱에서 KST로 계산해 `date`로 저장한다(DB 기본 시간대에 기대면 투데이가 오전 9시에 초기화될 수 있다). 백엔드와 PostgreSQL 컨테이너 모두 `TZ=Asia/Seoul`로 둔다. 방 배치는 `jsonb` 컬럼이다.

`events.type`은 MVP에서 다음 정도면 충분하다: `share_open`(공유 링크 열림), `mobile_notice`(모바일 안내 진입), `signup`, `session_start`(로그인 사용자 접속, 하루 1회), `furniture_move`.

## 3단계. 개발 환경과 첫 배포 (3\~4일)

저장소 하나에 프론트엔드, 백엔드, 3D 에셋을 모두 넣는다(모노레포). 1인 개발에서는 Claude Code가 세 폴더를 한 번에 보고 작업할 수 있어서 가장 편하다.

```
miniroom/
├── CLAUDE.md            # 프로젝트 규칙 (Claude Code가 매번 읽음)
├── docker-compose.yml   # backend + postgres
├── frontend/            # Vite + Three.js + React
│   └── public/models/   # 압축된 glb
├── backend/             # Spring Boot 4.x (Gradle)
├── assets/
│   ├── blender/         # 가구 생성 Python 스크립트, .blend 원본
│   └── export/          # 압축 전 glb
└── docs/                # PRD, API 명세, ERD
```

- **Docker Compose**: MVP는 `backend`와 `postgres` 컨테이너 두 개면 된다. 프론트엔드는 개발 중에는 `npm run dev`로 따로 띄운다.
- **CLAUDE.md**: PRD의 핵심 규칙(가구 규격, 성능 예산, API 경로 규칙)과 폴더 구조를 적어둔다. 새 작업을 시킬 때마다 설명을 반복하지 않아도 된다.
- **Git**: GitHub 저장소를 만들고 `main` 브랜치 하나에 기능 단위로 작은 커밋을 쌓는다. 1인 개발이라 복잡한 브랜치 전략은 필요 없다.
- **환경 변수**: Google OAuth 클라이언트 ID와 DB 비밀번호는 `.env`에 두고 `.gitignore`에 넣는다.
- **로컬 개발**: Vite dev server의 proxy로 `/api`, `/oauth2`, `/login`을 백엔드(8080)로 넘긴다. 프론트와 백엔드가 같은 주소처럼 보여서 로컬에서는 쿠키와 CORS 문제가 생기지 않는다.
- **첫 배포 (워킹 스켈레톤)**: 이 단계 안에 "빈 화면 + Google 로그인 + `/api/me`"만 실제 도메인에 올린다. 프론트(루트 도메인)와 백엔드(`api.` 서브도메인)가 나뉜 구조에서는 세션 쿠키 도메인, SameSite, CORS credentials, CSRF, 로그인 후 리디렉션 문제가 배포 환경에서만 드러난다. 5단계에서 처음 만나면 테스트 일정이 밀린다. 이후 4단계 동안 매주 금요일에 배포한다.

## 4단계. MVP 구현 (4주)

1주에 하나씩, 매주 끝에 "실제로 눌러볼 수 있는 것"이 남도록 쪼갠다. 4주차가 끝나면 두 계정으로 핵심 루프를 한 바퀴 돌 수 있어야 한다.

| 주차 | 목표 | 만들 것 | 끝났다는 기준 |
| --- | --- | --- | --- |
| 1주차 | 백엔드 기반 | 엔티티(slug, nickname, events 포함), Google 로그인, 첫 로그인 때 방 자동 생성, 닉네임과 약관 동의 API, 방 조회와 저장 API(배치 검증 포함) | Swagger에서 방을 저장하고 다시 조회됨. 배포 서버에서도 로그인됨 |
| 2주차 | 3D 방 보기 | 기술 검증 코드 정리, API로 받은 배치대로 방 렌더링, 첫 가입 화면, 로그인 후 원래 방으로 복귀, 가구 17종 제작과 압축 | 방 링크로 들어가면 가구가 놓인 방이 보이고, 로그인하고 돌아와도 같은 방 |
| 3주차 | 꾸미기 모드 | 가구 목록 패널, 배치와 회전, 바닥과 벽지 선택, 저장 | 새로고침해도 배치가 그대로 남음 |
| 4주차 | 방명록과 방문 | 방명록 작성, 조회, 삭제, 도배 방지, 투데이 카운트, 새 글 개수, 공유 링크(`/s/{slug}`)와 OG 태그, 모바일 안내 페이지, 이벤트 기록, 탈퇴, 약관 페이지 | 두 계정으로 방문, 방명록, 답방이 한 바퀴 돎. 카카오톡에 링크를 보내면 미리보기가 뜸 |

가구 17종 제작은 2주차에 몰지 말고, 1주차부터 저녁마다 Blender로 몇 개씩 만들어 두면 일정이 여유로워진다. 4주차 작업량이 가장 많으므로 밀리면 도배 방지와 탈퇴 화면은 5단계 초반으로 넘기되, 지인 테스트 시작 전에는 반드시 끝낸다.

## 5단계. 배포와 지인 테스트 (2\~3주)

배포는 가장 단순하게 한다. 서버 한 대에 Docker Compose를 그대로 올리고, 프론트엔드와 glb는 정적 호스팅에 올려 CDN 효과를 공짜로 얻는다.

- **백엔드**: 클라우드 VM 한 대(AWS Lightsail이나 EC2 같은 소형 인스턴스)에 `docker compose up`. PostgreSQL 데이터는 볼륨으로 보관하고 하루 한 번 백업한다.
- **프론트엔드와 에셋**: Cloudflare Pages나 Vercel 같은 정적 호스팅. 빌드 결과와 glb가 CDN으로 자동 배포된다.
- **도메인과 HTTPS**: 3단계 첫 배포 때 이미 만들어 둔 구성을 그대로 쓴다. 프론트는 루트, 백엔드는 `api.` 서브도메인이고, Google OAuth 리디렉션 주소도 그때 등록되어 있다.
- **Google OAuth 게시 상태**: OAuth 동의 화면이 "테스트" 상태면 등록한 테스트 사용자만 로그인할 수 있다. 지인 테스트 전에 "프로덕션"으로 바꾼다. 이메일과 프로필만 요청하므로 별도 심사 없이 전환된다.
- **지표 측정**: 별도 분석 도구 없이 SQL로 PRD 지표(방명록 교환율, 꾸미기 완료율, 답방률, D7 리텐션, 초대 전환율)를 계산한다. 방문, 방명록, events 테이블로 모두 나온다. 테스트 시작 전에 지표별 SQL을 `docs/metrics.sql`에 미리 써 두고, 더미 데이터로 결과를 확인한다.
- **출시 전 점검**: 개인정보처리방침과 이용약관 페이지, 탈퇴 동작, 14세 확인, DB 백업 복원 테스트를 한 번씩 확인한다.
- **지인 테스트**: 지인 100명에게 2주 동안 써보게 하고, 끝나면 짧은 설문으로 이유를 묻는다. D7 리텐션을 재려면 가입 후 13일이 지나야 하므로 첫 주 안에 가입을 몰아서 받는다. PRD의 첫 관문(D7 리텐션 25%)을 넘으면 베타 기능으로 넘어간다.

## 단계별 Claude Code 활용법

Claude Code에는 한 번에 큰 기능을 맡기지 말고, 이 문서의 표 한 줄 단위로 요청한다. 작게 시키고 매번 직접 실행해 확인하는 것이 가장 빠르다.
