# 3D 미니룸 커뮤니티 PRD (가칭)

Sep 30, 2026 · @현철

## 개요

내 3D 방을 꾸미고, 친구 방에 놀러 가 방명록을 남기는 웹 기반 3D 소셜 커뮤니티다. 싸이월드 미니홈피의 "나만의 공간, 일촌, 방명록" 구조를 설치 없이 브라우저에서 돌아가는 3D 경험으로 다시 만든다.

비전은 알고리즘 피드를 넘기는 SNS가 아니라, 친구의 공간에 "놀러 가는" SNS다.

- **내 공간의 소유감**: 가구 하나, 벽지 한 장까지 내가 고른 방이 곧 내 프로필이다.
- **느리고 따뜻한 관계**: 좋아요 숫자보다 방명록 한 줄, 방문자 수가 관계의 단위다.
- **설치 없는 3D**: 링크 하나로 PC 브라우저에서 바로 친구 방에 들어간다. 모바일은 1차 지원 대상에서 제외한다.

## 배경과 기회

"내 공간을 꾸미고 친구가 놀러 오는" 경험을 주는 서비스는 지금 비어 있다.

- **향수와 수요**: 2000년대 싸이월드 세대는 지금 30\~40대가 되었고, 10\~20대는 Y2K 감성과 꾸미기(다꾸, 폰꾸) 문화를 즐긴다.
- **피드 피로**: 인스타그램, 틱톡 같은 알고리즘 피드는 보여주기와 비교에 지쳤다는 반응이 많다. 가까운 사람과의 작은 공간에 대한 수요가 있다.
- **기술 성숙**: Messenger(abeto) 같은 사례가 WebGL, Three.js만으로 모바일 브라우저에서도 부드러운 3D 공간을 보여줬다. 앱 설치 없이 링크로 공유되는 점이 확산에 유리하다.
- **경쟁 공백**: 제페토 같은 메타버스는 앱 기반에 아바타 중심이고, 싸이월드의 재출시 시도는 3D 공간 경험을 보여주지 못했다. "웹 링크로 들어가는 개인 3D 방" 포지션은 아직 뚜렷한 강자가 없다.

## 타깃 사용자

첫 타깃은 친한 친구끼리 링크를 주고받는 20\~30대다. 크리에이터는 정식 출시 이후 공급자 역할로 들어온다.

| 페르소나 | 상황 | 원하는 것 | 걸림돌 |
| --- | --- | --- | --- |
| 지은 (34, 직장인) | 싸이월드 세대, 인스타는 눈팅만 함 | 옛 친구들과 부담 없이 안부 나누기 | 새 앱 설치와 가입이 귀찮음 |
| 민준 (22, 대학생) | Y2K 감성, 다꾸와 폰꾸를 즐김 | 남들과 다른 내 방, 자랑할 거리 | 무료로 꾸밀 수 있는 게 적으면 금방 떠남 |
| 서연 (28, 3D 아티스트) | Blender로 소품을 만들어 봄 | 내가 만든 가구를 팔아 수익 얻기 | 제작 규격과 심사 기준이 불명확함 |

## 핵심 기능

MVP는 "방을 꾸미고, 링크로 초대하고, 방명록을 받는" 루프 하나만 검증한다. 링크를 받은 사람이 실제로 방명록을 남기고 자기 방을 만드는지만 확인되면, 나머지는 그다음에 만든다. 구현량을 줄이려고 로그인은 Google 하나, 방은 1인 1개, 카메라는 고정 쿼터뷰로 둔다.

| 기능 | 설명 | 우선순위 |
| --- | --- | --- |
| 로그인 | Google 로그인 하나만. 첫 로그인 때 닉네임 설정(Google 실명은 공개하지 않음). 로그인 후 원래 보던 방으로 복귀 | P0 MVP |
| 3D 미니룸 | 1인 1개, 기본 6×6m(12×12칸), 쿼터뷰 고정 각도에서 화면을 끌어 옮기고 확대·축소, 바닥과 벽지 교체 | P0 MVP |
| 방 넓히기 | 4칸씩 16×16, 20×20, 최대 24×24칸(12×12m). MVP는 결제 없이 지인 테스트 이벤트로 확장권 지급, 베타부터 도토리 | P0 MVP(확장권) / P1 베타(도토리) |

| 일촌 | 친구 신청과 수락, 서로 부르는 일촌명 | P1 베타 |

## MVP 가구 목록

MVP 가구는 17종이다. 2000년대 초 자취방 느낌(브라운관 TV, CD 플레이어, 곰인형)으로 미니룸의 향수를 살리고, 모든 가구가 팔레트 텍스처 한 장을 공유해 가볍게 만든다. 크기의 1칸은 0.5m × 0.5m, 방 바닥은 8×8칸이다.

| 창문 | 벽 장식 | 벽 슬롯 1개 | 벽 |

| 벽시계 | 벽 장식 | 벽 슬롯 1개 | 벽 |

바닥 3종(원목 마루, 체크 장판, 카펫)과 벽지 3종(아이보리, 하늘색 체크, 딸기 무늬)은 가구와 별개로 텍스처만 바꾼다.

구현을 줄이는 규칙은 다섯 가지다.

- 가구는 쌓지 않는다. 책상 위 모니터처럼 붙어 있는 것은 한 세트로 만든다.
- 벽 장식은 자유 배치 대신 벽 2면에 3개씩, 정해진 슬롯에만 건다.
- 겹침 판정은 칸 단위로만 한다. 러그만 예외이고, 러그끼리는 겹치지 않는다.
- 색상 변형은 MVP에서 만들지 않는다.
- 방당 가구는 벽 장식을 포함해 최대 30개다. 드로우콜 예산(100회)을 지키기 위한 상한이다.

배치는 가구의 중심점이 아니라 "기준 칸(왼쪽 위 칸의 x, y) + 회전(0, 90, 180, 270)"으로 저장한다. 3×2처럼 정사각형이 아닌 가구도 이 두 값만 있으면 차지하는 칸을 계산할 수 있고, 겹침 판정도 같은 계산을 쓴다. 벽 장식은 `슬롯 번호(0~5)`만 저장한다.

## 주요 사용자 흐름

핵심 루프는 "방문, 방명록, 내 방 꾸미기, 초대, 답방"이다. 알림 없이도 다음 접속 때 새 방명록 개수가 보이면 답방이 일어나는지 확인한다.

1. 친구가 보낸 방 링크로 들어와 로그인 없이 친구 방을 구경한다.
2. 방명록을 쓰려는 순간 Google로 로그인한다. 처음이면 닉네임을 정하고, 보던 친구 방으로 돌아온다. 쓰던 글은 그대로 남아 있다.
3. 첫 로그인 때 내 방이 자동으로 생긴다. 빈 방 대신 기본 가구 몇 개가 놓인 상태로 시작한다. 방명록을 남기면 "내 방 가보기" 버튼이 보인다.
4. 가구를 옮기고 바꾸며 내 방을 꾸민다.
5. 내 방 링크를 복사해 친구에게 보낸다.
6. 다음 접속 때 새 방명록 개수를 보고, 글쓴이의 방으로 답방한다.

링크를 눌렀을 때 3초 안에 방이 보여야 한다. 공유 링크로 퍼지는 서비스라 첫 로딩이 곧 전환율이다.

## 기술 아키텍처

무거운 3D 에셋은 미리 압축해 CDN에 두고, 서버는 "어떤 가구를 어디에 놨는지" 담은 가벼운 JSON만 주고받는다. 이 분리가 빠른 로딩과 낮은 서버 비용의 핵심이다.

&#91;embedded content: 시스템 구조 · 에셋 파이프라인, 클라이언트, 백엔드\]

방 하나는 `{바닥, 벽지, 가구 ID + 기준 칸 + 회전, 벽 장식 ID + 슬롯}` 목록인 JSON 한 개로 저장된다. 클라이언트는 이 JSON을 받아 필요한 glb만 CDN에서 내려받는다.

백엔드는 Spring Boot 하나로 API와 실시간 채널을 함께 운영하고, 전체를 Docker Compose로 묶는다. MVP는 PostgreSQL 하나로 시작하고, MongoDB는 필요가 확인될 때 붙인다.

| 구성요소 | 역할 | 도입 시점 |
| --- | --- | --- |
| Spring Boot 4.x (Java 25) | REST API, Spring Security + Google OAuth2 로그인, JPA | MVP |
| PostgreSQL 17 | 유저, 방명록, 방문 카운트, 지표용 이벤트 로그. 방 배치는 `jsonb` 컬럼에 저장 | MVP |
| Docker Compose | backend, postgres 컨테이너를 로컬과 서버에서 같은 설정으로 실행 | MVP |
| Redis | 투데이 카운트, 현재 접속자, 캐시 (MVP는 PostgreSQL로 카운트) | 베타 |
| Spring WebSocket (STOMP) | 방별 채널로 방문자 위치, 말풍선, 이모트 전달 | 베타 |
| S3 호환 스토리지 | 사진첩 이미지 | 베타 |
| MongoDB | 채팅 로그, 다이어리처럼 양이 많고 구조가 자주 바뀌는 데이터 | 필요 시 |

MongoDB를 처음부터 넣지 않는 이유는 두 가지다. 방명록, 일촌, 결제는 관계와 트랜잭션이 중요해 관계형 DB가 맞고, 방 배치 JSON도 PostgreSQL의 `jsonb` 컬럼으로 충분하다. DB를 두 개 운영하면 백업, 모니터링, 학습 부담도 두 배가 된다.

## 수익 모델

싸이월드의 도토리처럼 가상 화폐로 꾸미기 아이템을 파는 것이 주 수익원이다. 광고는 공간의 분위기를 해치므로 초기에는 넣지 않는다.

- **도토리(가칭) 충전**: 가구, 벽지, 미니미 옷, BGM을 도토리로 구매한다. 무료 기본 세트는 넉넉히 준다.
- **시즌 테마 팩**: 크리스마스, 벚꽃, 여름 바다 같은 한정 세트로 재방문과 구매를 동시에 만든다.
- **프리미엄 구독**: 방 확장, 방 여러 개, 방문자 통계, 다이어리 무제한.
- **크리에이터 마켓 수수료**: 유저 제작 아이템 판매액의 일부(정식 이후).
- **원칙**: 확률형 뽑기 없이 원하는 아이템을 직접 구매하는 방식만 둔다. 규제 부담과 유저 반감을 함께 줄인다.

## 성공 지표

MVP의 북극성 지표는 "주간 방명록을 주고받은 사용자 비율"이다. 관계가 실제로 오가는지를 가장 직접 보여준다. 아래 목표치는 검증 전 가설이다.

| 지표 | 정의 | MVP 목표 |
| --- | --- | --- |
| 주간 방명록 교환율 | 주간 활성 사용자 중 같은 주에 방명록을 1개 이상 쓰고 1개 이상 받은 비율 | 30% |
| 꾸미기 완료율 | 가입자 중 가구 5개 이상 옮기거나 추가한 비율 | 60% |
| 답방률 | 방명록을 받은 사용자가 7일 안에 글쓴이 방을 방문한 비율 | 40% |
| D7 리텐션 | 가입일 기준 7일째부터 13일째 사이에 1번 이상 접속한 가입자 비율 | 25% |
| 초대 전환율 | 공유 링크로 처음 들어온 비로그인 방문자 중 7일 안에 가입한 비율 (PC, 모바일 따로 집계) | 20% |

지표는 별도 분석 도구 없이 SQL로 계산한다. 방문, 방명록 테이블만으로는 "공유 링크로 들어왔는지", "비로그인 방문자가 나중에 가입했는지", "주인이 자기 방에 접속했는지"를 알 수 없으므로 `events` 테이블 하나에 접속, 공유 링크 유입, 모바일 안내 페이지 진입, 가입, 가구 이동을 기록한다. 비로그인 때 쓰던 `visitor_key`는 가입 순간 유저에 연결한다.

## 로드맵

첫 3개월은 혼자서도 돌아가는 비동기 기능(꾸미기, 방명록)만 만든다. 실시간 기능은 개발과 운영 부담이 커서, 루프가 검증된 뒤에 붙인다.

&#91;embedded content: 로드맵 · 3단계, 관문 2개\]

지인 100명 테스트에서 D7 리텐션 25%를 넘으면 베타로, 베타 1,000명 중 3% 이상이 도토리를 충전하면 정식 출시로 간다. 관문을 못 넘으면 다음 기능 대신 핵심 루프를 고친다.

두 번째 관문(도토리 충전)을 재려면 베타 중에 유료 결제가 열려 있어야 한다. 결제에는 사업자 등록, 통신판매업 신고, PG사 계약과 심사, 환불 정책과 약관 개정이 먼저 필요하고 PG 심사에만 몇 주가 걸릴 수 있다. 베타 시작과 동시에 이 준비를 시작한다.

## 리스크와 열린 질문

가장 큰 리스크는 기술이 아니라 "친구가 없는 빈 방"이다. 초기에는 지인 그룹 단위로 한꺼번에 들여오는 전략이 필요하다.

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 빈 방 문제 | 친구가 없으면 방명록 루프가 안 돎 | 모임, 동아리 단위 초대 이벤트. 로그인 없이 구경 가능한 링크 |
| 모바일에서 열리는 초대 링크 | 카카오톡 링크는 대부분 폰에서 열려, PC 전용이면 초대 전환이 끊김 | 모바일 안내 페이지에서 "내 PC로 링크 보내기"(이메일, 카카오톡 나에게 보내기) 제공. 초대 전환율을 기기별로 측정 |
| 에셋 제작량 | 가구가 적으면 꾸미는 재미가 금방 끝남 | Blender + Claude로 스크립트 생성, 스타일 가이드 고정, MVP는 가구 17종으로 시작 |

| 방명록 악용 | 욕설, 괴롭힘으로 커뮤니티 분위기 악화 | MVP는 삭제와 도배 방지, 베타에 필터, 신고, 차단, 방명록 공개 범위 설정 |
